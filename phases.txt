PHASE 2: DATABASE SCHEMA & CORE DATA MODEL IMPLEMENTATION (SQLite)
================================================================================
Goal: Implement a reliable, local SQLite storage layer that models sources,
      candidate obligations, confirmed deadlines, reminders, and audit trails.

2.1 Data Entities & Schema Definition
    - Table 1: `sources`
      * id: TEXT PRIMARY KEY (UUID4)
      * title: TEXT NOT NULL (e.g., filename or "Pasted Snippet - Oct 14")
      * raw_text: TEXT NOT NULL
      * source_type: TEXT NOT NULL ('email', 'pdf', 'sms', 'receipt', 'manual')
      * file_hash: TEXT (SHA-256 to prevent duplicate processing)
      * created_at: DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP

    - Table 2: `deadlines`
      * id: TEXT PRIMARY KEY (UUID4)
      * source_id: TEXT NOT NULL (FOREIGN KEY -> sources.id)
      * provider_name: TEXT NOT NULL (e.g., "Netflix", "Airtel", "HDFC ERGO")
      * category: TEXT NOT NULL ('subscription', 'insurance', 'broadband',
        'mobile', 'utility', 'dth', 'return_window', 'other')
      * obligation_type: TEXT NOT NULL ('payment_due', 'renewal', 'trial_ending',
        'validity_expiry', 'cancellation_deadline', 'return_deadline')
      * candidate_date: TEXT NOT NULL (ISO 8601 YYYY-MM-DD or YYYY-MM-DDTHH:MM:SS)
      * original_date_str: TEXT (Raw string found in source, e.g., "20th Oct")
      * amount: REAL (Nullable)
      * currency: TEXT DEFAULT 'INR'
      * evidence_snippet: TEXT NOT NULL (Verbatim excerpt from source)
      * evidence_char_start: INTEGER
      * evidence_char_end: INTEGER
      * extraction_confidence: REAL (0.0 to 1.0)
      * verification_status: TEXT NOT NULL ('source_stated', 'user_confirmed',
        'estimated', 'unverified')
      * recurrence: TEXT ('one_time', 'monthly', 'annual', 'unconfirmed')
      * official_url: TEXT (Nullable - validated provider support URL)
      * next_step_instructions: TEXT (Nullable checklist/summary)
      * status: TEXT NOT NULL ('needs_review', 'confirmed', 'upcoming',
        'action_needed', 'completed', 'cancelled', 'date_unverified')
      * owner: TEXT (Nullable, e.g. "Self", "Roommate")
      * created_at: DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
      * updated_at: DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP

    - Table 3: `reminders`
      * id: TEXT PRIMARY KEY (UUID4)
      * deadline_id: TEXT NOT NULL (FOREIGN KEY -> deadlines.id)
      * remind_at: DATETIME NOT NULL
      * lead_days: INTEGER NOT NULL (e.g., 7, 3, 1, 0)
      * status: TEXT NOT NULL ('scheduled', 'fired', 'dismissed')
      * created_at: DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP

    - Table 4: `audit_logs`
      * id: TEXT PRIMARY KEY (UUID4)
      * deadline_id: TEXT NOT NULL
      * action: TEXT NOT NULL ('extracted', 'user_edited', 'confirmed',
        'status_changed', 'reminder_created')
      * previous_value: TEXT (JSON string)
      * new_value: TEXT (JSON string)
      * timestamp: DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP

2.2 Database Layer Implementation
    - Create `backend/app/database.py` with async connection pool using aiosqlite.
    - Write idempotent database migrations/initialization logic creating tables
      and indexes on `status`, `candidate_date`, and `source_id`.
    - Implement CRUD operations in `backend/app/services/deadline_service.py`.

2.3 Verification & Validation Checklist:

PHASE 3: PARSING, EVIDENCE EXTRACTION & DETERMINISTIC ANALYSIS ENGINE
================================================================================
Goal: Build a high-precision, evidence-backed parser that extracts candidate
      deadlines, quotes verbatim snippets, handles date ambiguities responsibly,
      and operates at ₹0 cost without mandatory external AI APIs.

3.1 Ingestion & File Parsers
    - `text_parser.py`: Handles plain text, pasted email bodies, and SMS strings.
      Normalizes whitespace and tracks character offsets.
    - `email_parser.py`: Parses .eml or standard email headers (From, Subject,
      Date) and extracts body text (plain + HTML sanitization via standard lib).
    - `pdf_parser.py`: Extracts text and page coordinates using `pypdf`/`pdfplumber`.
      Gracefully detects scanned/image PDFs and reports "No readable text layer;
      please paste text or provide a digital PDF".

3.2 Deterministic Date & Keyword Extraction Engine
    - Build `date_extractor.py` combining regex patterns and `python-dateutil`:
      * Common Indian & Global formats: "DD/MM/YYYY", "DD-MM-YYYY",
        "Month DD, YYYY", "DD Month YYYY", "valid till DD-MMM".
      * Relative expressions: "renew in X days", "due in 48 hours".
      * Anchored patterns: matches following "due date:", "payment by:",
        "validity ends:", "renews on:", "trial ends on:".
    - Verbatim Evidence Span Tracking:
      * For every candidate date found, capture a surrounding window of text
        (e.g., ~120 characters or the full sentence) as `evidence_snippet`.
      * Record start and end character indices within the source document.

3.3 Obligation Classifier & Safety Rules
    - Category & Obligation Type detection (`obligation_classifier.py`):
      * Free trial renewal: keywords ("trial", "renews at", "cancel anytime before").
      * Utilities / Broadband: keywords ("bill period", "units consumed", "due date").
      * Insurance: keywords ("premium", "policy number", "renewal date").
      * Validity / Recharge: keywords ("plan validity", "pack expires", "recharge").
    - Strict Uncertainty Rules (Scenario D compliance):
      * If a date matches vague phrases like "sometime this month", "near the end
        of the month", or "early next week", DO NOT fabricate a specific calendar date!
      * Mark status as `date_unverified` with `verification_status: 'unverified'`.
      * Return explicit flag `requires_user_input: True` with instruction asking
        the user to confirm exact day or upload a bill notice.
    - Graceful AI Enhancement Layer (Zero-cost optional):
      * Deterministic parsing runs first and acts as the ground truth.
      * If local Ollama (e.g. llama3.2:1b or mistral:7b) is installed locally,
        allow an optional semantic extraction pass; if not installed or unreachable,
        silently and cleanly use the 100% deterministic engine.
      * Never fail if no LLM is running.

3.4 Verification & Validation Checklist:
    [ ] Test suite with 15+ curated test cases:
        - Definite due date extraction with exact quoted snippet.
        - Trial expiration extraction with cancellation condition.
        - Ambiguous text ("near end of month") flagged as `date_unverified`.
        - Source without date triggers graceful empty candidates message.
    [ ] All extracted dates have 100% matching verbatim evidence in source.

PHASE 4: SELF-HOSTED MCP SERVER DEVELOPMENT (SPEC 2025-11-25+, STREAMABLE HTTP)
================================================================================
Goal: Implement the core hackathon requirement: an official MCP (Model Context
      Protocol) server following specification version 2025-11-25 or later,
      running over Streamable HTTP transport with production-grade tools.

4.1 MCP Server Architecture & Transport Setup
    - Utilize official Python MCP SDK with Streamable HTTP transport handler.
    - Server endpoint: `/mcp` (supports HTTP POST for JSON-RPC 2.0 messages and
      HTTP GET for Server-Sent Events / SSE streamable transport).
    - Server identification:
      * Name: "deadline-rescue-mcp"
      * Version: "1.0.0"
      * Protocol Specification: "2025-11-25"

4.2 Real MCP Tool Implementation (No static mocks!)
    Implement all 8 core tools defined in idea.md:
    1. `ingest_source(raw_text: str, title: str, source_type: str) -> dict`
       - Stores raw source into SQLite `sources` table.
       - Returns `{"source_id": str, "title": str, "char_count": int}`.
    2. `find_deadline_candidates(source_id: str) -> list[dict]`
       - Runs extraction engine against the given source.
       - Stores candidate rows in `deadlines` with status `needs_review` or
         `date_unverified`.
       - Returns candidate objects with evidence spans, provider, date, confidence.
    3. `get_deadline_evidence(deadline_id: str) -> dict`
       - Fetches the verbatim quote, source title, and full context snippet.
       - Guarantees exact 1:1 match with database record.
    4. `confirm_or_correct_deadline(deadline_id: str, confirmed_date: str, provider_name: str, notes: str) -> dict`
       - Updates deadline record to status `confirmed` or `upcoming`.
       - Records previous extraction vs user correction in `audit_logs`.
    5. `create_follow_up(deadline_id: str, lead_days: list[int], export_calendar: bool) -> dict`
       - Creates reminder schedule (e.g. 7 days and 1 day prior).
       - Updates deadline status to `upcoming`.
       - Generates downloadable `.ics` data if requested.
    6. `prepare_next_step(deadline_id: str) -> dict`
       - Returns action checklist and validated official support URL
         (e.g., Netflix cancellation page, Airtel payment page, HDFC ERGO renewal).
       - Clearly marks limitation if no verified official URL exists.
    7. `update_deadline_status(deadline_id: str, new_status: str, resolution_notes: str) -> dict`
       - Transitions state: `completed`, `cancelled`, `action_needed`.
       - Strictly enforces: user confirmation != external provider payment.
    8. `list_deadlines(status_filter: str, category_filter: str) -> list[dict]`
       - Returns filtered active, upcoming, overdue, or resolved obligations.

4.3 Tool Schema & JSON-RPC Compliance
    - Define strict Pydantic schemas for all inputs and outputs.
    - Full error handling conforming to JSON-RPC 2.0 error codes:
      * Invalid params (-32602)
      * Method not found (-32601)
      * Internal error (-32603) with readable diagnostic message.

4.4 Verification & Validation Checklist:
    [ ] Direct curl / HTTP test sending `tools/list` returns all 8 registered tools
        with accurate parameter definitions.
    [ ] Direct `tools/call` for `ingest_source` followed by `find_deadline_candidates`
        successfully executes and commits to SQLite.
    [ ] Response headers and SSE streams comply with MCP spec 2025-11-25.

PHASE 5: BACKEND APPLICATION LAYER, AGENT HOST & MCP CLIENT INTEGRATION
================================================================================
Goal: Connect the web application to the MCP server using a real MCP client
      bridge, enabling conversational queries and direct tool invocation with
      complete tool-call observability for hackathon judges.

5.1 FastAPI Backend Endpoints (`backend/app/main.py`)
    - `/api/sources/upload`: Multipart file / text ingestion route.
    - `/api/deadlines`: Direct REST route for querying and managing deadlines.
    - `/api/deadlines/{id}/ics`: Downloadable iCalendar file endpoint.
    - `/api/agent/chat`: Conversational agent endpoint that parses natural
      language (e.g., "I started a free trial, tell me when it charges me"),
      routes requests through the MCP client, invokes MCP tools, and returns
      evidence-backed responses.
    - `/api/mcp/log`: Live stream / history of all MCP tool invocations
      (tool name, input arguments, execution time, output payload, status).

5.2 In-Process MCP Client Bridge (`backend/app/services/mcp_client.py`)
    - Client connects directly to the Streamable HTTP MCP server endpoint.
    - Captures and logs all tool invocations for the visual inspection panel.
    - Guarantees that every conversational action actually passes through the
      MCP protocol layer rather than bypassing it with private function calls.

5.3 Deterministic Conversational Agent Handler
    - Maps common natural language intents to MCP tools:
      * "Check this bill / trial email" -> `ingest_source` -> `find_deadline_candidates`
      * "Show evidence for Netflix" -> `get_deadline_evidence`
      * "Confirm this date" -> `confirm_or_correct_deadline`
      * "Remind me 3 days before" -> `create_follow_up`
      * "How do I cancel?" -> `prepare_next_step`
      * "I paid this bill" -> `update_deadline_status`
      * "What is due this week?" -> `list_deadlines`
    - Formats output responses strictly emphasizing:
      * The extracted date in bold.
      * The exact quoted evidence.
      * Explicit confirmation prompts (never assuming confirmation).

5.4 Verification & Validation Checklist:
    [ ] End-to-end API test: upload text -> agent responds with evidence quote
        and candidate date -> MCP log records `ingest_source` and
        `find_deadline_candidates` invocations.
    [ ] `.ics` download endpoint returns valid RFC 5545 calendar file.
